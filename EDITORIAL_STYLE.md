# ReadSigil: practical English and case experience

Updated: 17 October 2026

## The rule

Put the reader into the management situation immediately. Open with the commercial problem, the conflicting figures, the deadline and the decision to be made. Use clear business English, not training-course or model-evaluation language.

A case should proceed: **What is happening? → Where is the problem concentrated? → What explains it? → What would we do, for whom, through whom? → What would prove it worked?**

## Say this, not that

| Avoid in participant-facing copy | Prefer |
| --- | --- |
| Choose your first evidence request | Which report would you check first? |
| Request evidence | Ask to see the report / Get the information |
| No answer key until after your decision | Make your recommendation, then review the analysis |
| Unlock the debrief | Submit recommendation · Review analysis |
| Decision sealed | Recommendation recorded |
| Expert reasoning held | The analysis follows your recommendation |
| Simulated consequence | Case outcome |
| Try counterfactual | What if the conditions changed? |
| Challenge the assumed rate | Change the assumed rate |
| Falsifiable intervention | Specific action with a measurable result and stop condition |
| Research preview (in a case heading) | Put the case title and decision first; methodological details belong in the notes |
| Synthetic dataset (in the case briefing) | Explain the case situation and numbers, with construction details in the common notes |

Use `customer base`, `reports`, `financial impact`, `risk`, `operating capacity`, `decision owner`, `control group`, `uplift`, `confidence interval`, `calibration`, `incremental contribution` and `cost of delay` wherever technically appropriate. Do **not** ban precise statistical terminology.

## Experience checks before publication

1. The first screen gives the reader a role, a problem and a consequential question; it is not an instructional disclaimer.
2. Labels sound natural when spoken aloud by a CEO, branch manager, CFO, CIO or operations head.
3. Show the figures and their definitions, not an abstract matrix or teaching framework, before the reader can act.
4. Do not pretend that demonstrations are actual client results. Keep short disclosures in the shared footer notes (`/case-notes.html`), except when omission would misrepresent an interactive tool's real capability.
5. If the interface only plays back scripted results, do not call it a live engine. If a case is fictional, keep that fact accessible without repeatedly inserting it into dialogue.
6. Update cache-busting query versions when changing externally loaded JS/CSS. Check UI strings in inline scripts and generated content, not just visible HTML.
7. Test button text against actual behaviour. Do not label a button "download" or "submit" unless it does that.
8. Preserve technical explanations and citations in real research, tutorials and methods articles; these aren't case-dialogue problems.

## Audit record

On 17 October 2026 the source-copy audit covered the repository's **108 HTML pages** and core interactive JavaScript for Case Lab, the Casebook, Decision Atlas Studio, Navigator, Build Lab, Playground, utilities and games. The highest-priority participant-facing copy was revised.

The changed website files were checked for removed phrases and edited JavaScript parsed successfully. This is a *source-copy audit*, not a complete visual accessibility, responsive-layout or real-user usability study. Public CDN and search caches may serve earlier content until refreshed.

**Remaining structural work:** Case Lab still uses scored multiple-choice rounds. Changing copy does not eliminate the classroom feel of that interaction. A substantive redesign would require staged management information, optional investigations, free-form decisions and measured economic consequences. Preserve the ability to compare decisions against a benchmark without presenting an "answer key" in advance.
