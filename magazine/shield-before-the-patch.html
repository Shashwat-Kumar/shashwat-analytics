OpenAI and Cisco open-sourced a way to block an exploit on a running server while the patch is still being tested

Shirudo, released on 23 November, lets an AI agent write a small, signed kernel-level 'shield' that blocks the code path a vulnerability needs, without restarting the service. Operators approve each shield before it loads. For firms whose risk sits in the weeks between disclosure and patch, it is a new kind of temporary control, and it needs an owner and an expiry date.

By Shashwat Kumar · 2026-11-24 · 4 min read · Analysis

Facts are attributed and linked to their sources. The analysis and opinions are the author's own.

What it is

On 23 November OpenAI and Cisco launched Shirudo, Japanese for "shield", as an open-source runtime for protecting Linux systems while patches are rolled out. It uses eBPF, a Linux technology that runs small programs at specific points inside the operating system, to observe suspicious activity and block the specific behaviour a vulnerability depends on, while letting legitimate requests through. Teams can watch how a proposed shield would affect applications before enforcing it, and deploy it once an operator approves, with the service still running.

In OpenAI's example, its Codex model generated a shield that added an input check to Java's Base64 decoder and attached it to a running Elasticsearch process; the shield rejected the exploit attempt without a restart. Shields are cryptographically signed and verified before loading, checked by Linux's own eBPF verifier, and a hardware Trusted Platform Module keeps a verifiable record of protections being loaded or removed. The code is under the BSD 2-Clause licence, with the BPF programs dual-licensed under BSD and GPL. The companies say they want tested shields to ship alongside vulnerability disclosures, and have scheduled a technical webinar for 15 December.

Why it matters

Issue 04 looked at the price of the patch gap: AI is finding vulnerabilities faster than organisations can test and deploy fixes. As OpenAI puts it, testing and deploying a patch can still take days or weeks, and blocking the vulnerable operation outright could take the service offline. Shirudo is aimed squarely at that window, and it pairs AI-written defences with the evidence an auditor will want: a signature, an approval and a hardware-backed record of when the shield went on and came off.

A shield is a temporary control. Give every one an owner and an expiry date, or temporary quietly becomes permanent.

In my view the risk is organisational, not technical. A shield is a change to how production systems behave, written by an agent. It should go through emergency change management with a named approver, a test against real traffic, and a date by which the real patch must replace it. Without that, a firm can accumulate dozens of unreviewed kernel rules that nobody remembers adding, which is its own kind of vulnerability.

What I'd watch

  • Whether Linux distributions or major vendors start publishing tested shields alongside their security advisories.
  • False-positive rates in real deployments: how often a shield blocks legitimate traffic.
  • Whether change-management and audit tools can read Shirudo's signed load and removal records directly.
