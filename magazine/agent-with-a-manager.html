Microsoft will give AI agents their own mailbox, their own permissions and a named manager. That is what makes one answerable

On 19 November Microsoft said agents built in Foundry can be issued their own Entra identity and Microsoft 365 account, a manager in the org chart who is accountable for them, an audit trail of their own and a kill switch that disables every copy of a design at once. It is the most complete vendor answer yet to the question banks are now asking: on whose authority did the agent act?

By Shashwat Kumar · 2026-11-24 · 6 min read · Analysis

Facts are attributed and linked to their sources. The analysis and opinions are the author's own.

What it is

In a Microsoft Foundry blog post on 19 November, Microsoft described a new kind of agent that works "under its own identity as a named member of your organization". Each one has a Microsoft Entra agent identity and an agent user account, so it can take Microsoft 365 actions as itself and, Microsoft says, "never borrows anyone's credentials". It gets its own email, calendar and OneDrive; it is granted permissions the way a person would be; it has a manager who is accountable for it and appears in the org chart; and every action is attributed to the agent, "not to whoever happened to be in the conversation". These are the same type of agent as Autopilot in Microsoft 365 Copilot, which Microsoft builds; in Foundry, customers build their own.

Microsoft explains the problem it is solving. Without its own account, an agent can work in Outlook or Teams only with a user's permissions. That fails when the agent is triggered by an event and no one is signed in, so it either cannot act or has to store someone's credentials. It also fails in a group chat, where the agent has to guess whose behalf it is acting on, that person's access then applies to the whole thread, and members can see content they are not entitled to.

Agents are not built one at a time. A developer builds a blueprint that defines what the agent can do, such as which APIs and MCP tools it may call. Once an admin approves the blueprint, people in the organisation "hire" their own instances, and each manager decides which specific resources, such as which SharePoint site or Azure DevOps project, their instance can reach. Because every agent is an instance of a blueprint, Microsoft says "one kill switch can disable an entire class of agents in one action", with a control plane called Agent 365 for the fleet. Microsoft also announced Hermes Enterprise with Nous Research, whose open-source Hermes Agent it describes as the top agent on OpenRouter by token usage. A hosted service and a managed self-hosted option are listed as coming soon; a cookbook for self-hosting it as a Foundry agent is already on GitHub.

Other vendors are moving to finer-grained control from a different direction. In the same week, xAI's Grok Bot 1.2.3 changelog (18 November) added connector pages where each tool can be set to Always allow, Auto-review, Needs approval or Blocked, and let team admins limit which tools the built-in GitHub connector offers.

Why it matters

Microsoft frames identity as the way an organisation answers three questions about any action: who took it, were they authorised to, and can we prove it afterwards? Those are the questions an auditor asks, and they are what the banks in this week's cover story are trying to answer for their own agents. An agent that acts under a borrowed login cannot answer the first, and therefore cannot answer the other two.

The most useful passage in the post is about how agents differ from staff. Microsoft writes that an agent "has no stakes of its own", so accountability has to sit with the people around it; that it does not notice when it is past what it knows; and that "a thousand copies of one agent share the same blind spots and fail together." That last point is why a fleet-wide kill switch matters. A human workforce rarely fails all at once; a blueprint can.

Giving an agent an employee badge is the easy part. The control is the name of the manager printed on it, and whether that manager can explain what the agent did.

In my view there are two things to check before copying this. First, approval. At Microsoft, an employee can deploy one of these agents internally without a formal IT review if its blueprint stays within bounds agreed with Microsoft IT. That makes the bounds document the real control, and it should be owned and reviewed like any other access policy. Second, attack surface. An agent with its own mailbox can receive email, including phishing and instructions planted for it. Its own identity makes it traceable; it does not make it harder to trick.

What I'd watch

  • Whether agent identities are included in periodic access reviews and leaver processes, like staff accounts.
  • What an agent user account costs: whether each instance needs its own licence.
  • Whether Agent 365 audit records can be exported to an existing security monitoring system without extra tooling.
  • How many organisations use the blueprint kill switch in anger, and what it disables that was not expected.
